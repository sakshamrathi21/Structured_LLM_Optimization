\section{Evaluation}
\label{sec:eval}
We evaluate \textsc{Feather} across a range of models, GPU configurations, and real-world  datasets. Our evaluation seeks to answer the following questions:
\begin{enumerate}
    \item How does \textsc{Feather}'s performance scale across diverse workloads, varying numbers of prefix groups, decode lengths, and input sequence lengths?
    \item What gains does \textsc{Feather} deliver for both online and offline serving under real-world workloads?
    \item What is the contribution of each component of \textsc{Feather} to overall performance?
    \item How much does replacing individual components with ideas from prior work degrade throughput?
    \item What is the computational overhead introduced by \textsc{Feather}'s scheduling?
\end{enumerate}

\subsection{Experimental Setup}

\textbf{Models and Hardware.}
We evaluate on three model families spanning a range of sizes: Qwen~\cite{qwen} (2B),  LLaMA-3~\cite{llama3modelcard} (8B), and LongChat~\cite{longchat2023} (13B). Unless stated otherwise, all experiments run on an NVIDIA RTX 6000 Ada Generation GPU~\cite{nvidia_rtx6000_datasheet} with 48\,GB of HBM and a 96\,MB L2 cache, with the maximum batch size fixed at 500. \textcolor{red}{[Present results on A100 for PAT? Any other GPU?]}

\textbf{Workloads.}
Following prior work, request arrivals are modeled as a Poisson process, with input and output lengths sampled from two real-world datasets. L-Eval~\cite{an2023leval} is a benchmark of human-labeled query-response pairs covering diverse tasks such as summarization and question answering, with sequence lengths ranging from 2.7K to 210.5K tokens. LongBench~\cite{bai2024longbench2} is a curated collection of long-context samples drawn from 21 datasets across 6 task categories---including multi-document question answering, summarization, and code completion---with context lengths between 4K and 10K tokens.

\textbf{Baselines.}
We compare \textsc{Feather} against the following state-of-the-art LLM serving systems, all with prefix caching enabled by default. vLLM~\cite{kwon2023efficient} is evaluated under its default FCFS scheduling policy. SGLang~\cite{zheng2024sglangefficientexecutionstructured} is evaluated under all three of its supported scheduling policies---FCFS, LPM, and DFS-W---to provide a comprehensive comparison across its design space. Finally, DynamicBatching~\cite{pang2025optimizing} represents a recent approach specifically optimized 
for LLM inference batching.

\textbf{Metrics.}
We report three key metrics throughout our evaluation. Throughput (toks/s) measures the number of output tokens generated per second, reflecting overall serving capacity and GPU utilization. Time Between Tokens (TBT) captures the average time elapsed between consecutive decoded tokens, reflecting the smoothness and responsiveness of generation---a metric of particular importance in interactive serving settings. Finally, we also track the average batch size per forward pass, which helps understand the relationship between scheduling decisions and the above two metrics.

\subsection{End-to-End Comparison}

Throughout this section, we evaluate a workload consisting of 5 prefix groups, each of length 5000 tokens, with roughly equal request distribution across groups. Unless otherwise stated, the input request rate is 500 req/sec, each request generates 200 output tokens, and experiments run on the Llama3-8B model~\cite{llama3modelcard}. We vary each of these configuration parameters in turn to examine how \textsc{Feather} compares against all baselines. The maximum batch size is fixed at 500, and the token budget at 32768 tokens.

\subsubsection*{Varying Input Request Rate}

Figure~\ref{fig:tp_vs_rps_l_5000_fam_5} presents throughput (toks/s) as a function of the input Poisson rate. Across all policies, throughput rises with increasing request rate before eventually saturating. \textsc{Feather} consistently outperforms all baselines at every request rate. At 100 req/sec, \textsc{Feather} achieves roughly $4\times$ the throughput of vLLM's FCFS policy.

Notably, this throughput advantage is not driven by larger batch sizes. As shown in Figure~\ref{fig:abs_vs_rps_l_5000_fam_5}, \textsc{Feather} maintains a \emph{smaller} average batch size than vLLM:FCFS across all request rates. This reinforces a key insight: \emph{smaller, homogeneous batches outperform larger, heterogeneous ones}. The gradual growth in \textsc{Feather}'s batch size with increasing request rate reflects its ability to smartly (\textcolor{red}{better adverb here}) aggregate more requests from the same prefix group into the active batch without sacrificing locality. We also observe that SGLang policies consistently operate at lower batch sizes than vLLM policies; this is because vLLM avoids double-counting shared prefix tokens toward the token budget, allowing it to pack more requests into each batch.

Turning to time-between-tokens (TBT) in Figure~\ref{fig:tbt_vs_rps_l_5000_fam_5},\\ \textsc{Feather} achieves substantially lower TBT than all baselines except SGLang:FCFS, whose smaller batch sizes naturally yield faster per-token generation. While SGLang's LPM and DFS-W policies also operate at low batch sizes, their TBT remains significantly higher than \textsc{Feather}'s - a consequence of the non-trivial scheduling overhead incurred during their batch construction process (see \S for a detailed breakdown). Together, these results demonstrate that \textsc{Feather} strikes an effective balance between batch efficiency, cache locality, and scheduling overhead.

\subsubsection*{Varying Number of Prefix Groups}

Figures~\ref{fig:tp_vs_fam_l_5000}, \ref{fig:abs_vs_fam_l_5000}, and \ref{fig:tbt_vs_fam_l_5000} present throughput, average batch size, and TBT as a function of the number of prefix groups, respectively.

As established in \S\ref{sec:motivation}, increasing the number of prefix groups introduces request heterogeneity, which degrades both temporal and spatial locality in the KV cache. This manifests as a sharp drop in throughput under vLLM's FCFS policy even when moving from just 1 to 2 prefix groups. As the number of groups grows further, FCFS continues to suffer: beyond 20 prefix groups, the aggregate KV cache footprint exceeds HBM capacity, causing a pronounced collapse in average batch size (Figure~\ref{fig:abs_vs_fam_l_5000}) and a corresponding increase in recomputation, which further depresses throughput.

\textsc{Feather} mitigates this by co-scheduling requests that share a prefix group, improving cache reuse and reducing evictions. This allows \textsc{Feather} to sustain a larger effective batch size and significantly outperform all baselines in throughput across the entire range of prefix group configurations.

SGLang's LPM and DFS-W policies occupy a middle ground: their prefix-aware scheduling reduces KV cache evictions and supports larger batch sizes relative to FCFS, yielding higher throughput than vLLM:FCFS at scale. However, the additional per-step scheduler overhead inflates their TBT, making them less suitable when latency is a primary concern.
Overall, \textsc{Feather} achieves the best throughput across all settings while keeping TBT competitive.

\subsubsection*{Varying Number of Decode Tokens}
Figures~\ref{fig:tp_vs_tok_l_5000}, \ref{fig:abs_vs_tok_l_5000}, and \ref{fig:tbt_vs_tok_l_5000} present throughput, average batch size, and TBT as a function of the number of output decode tokens per request. Each decode token generation corresponds to a sweep through its entire KV cache. The policies exhibit two qualitatively distinct regimes separated by a crossover around 20 decode tokens. In the prefill-dominated regime (1--20 tokens), all policies behave similarly: throughput grows modestly and batch sizes converge, since the workload is dominated by short prefill phases that leave little room for locality-aware scheduling to take effect.

Beyond 20 tokens, the policies diverge sharply. \textsc{Feather} scales strongly with decode length, reaching roughly 3800 toks/s at 200 tokens --- more than $3\times$ the throughput of any SGLang policy at the same point. Two complementary effects drive this. First, longer decode phases mean each batch sweeps through the KV cache repeatedly, so the gains from temporal and spatial locality compound over more iterations, allowing \textsc{Feather} to utilize the benefits of locality for a larger fraction of total execution time. Second, longer decodes give the scheduler more opportunities to accumulate waiting requests from the same prefix group, enabling it to assemble larger, more homogeneous batches. Both effects reinforce each other as decode length grows, explaining the near-monotonic rise in \textsc{Feather}'s average batch size and throughput.

SGLang policies follow the opposite trajectory in batch size. Because SGLang counts shared prefix tokens toward the token budget, each prefill contributes roughly 5000 tokens to the overall token budget, while each decode step contributes only a single token. As requests become decode-heavy, fewer prefills occur per scheduling step, meaning fewer new requests are available at each step to populate the batch. This causes the effective batch size to collapse for SGLang policies (Figure~\ref{fig:abs_vs_tok_l_5000}). The resulting smaller batches reduce per-step compute, which drives down TBT for SGLang:FCFS and LPM, but at the cost of throughput, since fewer tokens are generated per second. Although \textsc{Feather} operates at a higher batch size than SGLang policies, its TBT remains competitive: reduced scheduler compute overhead and the gains from temporal and spatial locality together offset the cost of processing larger batches.

\subsubsection*{Varying Number of Shared Prefix Tokens}

Figures~\ref{fig:tp_vs_sys}, \ref{fig:abs_vs_sys}, and \ref{fig:tbt_vs_sys} present throughput, average batch size, and TBT as the shared prefix length increases from 100 to 10000 tokens. The overall trend is expected: longer prefixes increase prefill compute and KV cache memory pressure, dragging down throughput across all policies. What is more revealing is how differently the policies respond to this pressure.

At short prefix lengths, all policies perform similarly and throughput is comparable across the board. Beyond 1000 tokens, the policies diverge sharply. \textsc{Feather}'s throughput advantage grows with prefix length, a direct consequence of higher locality gains as sequences get longer. vLLM:FCFS, despite maintaining large batch sizes throughout (owing to its idea of excluding shared prefix tokens from the token budget), sees its throughput collapse and TBT increase exponentially to 1.0s at 10000 tokens because packing oversized, heterogeneous batches destroys locality. \textsc{Feather} avoids this by running moderately sized but homogeneous batches, keeping TBT nearly flat across the entire range. The SGLang policies tell a  different story: because SGLang counts prefix tokens toward the token budget, longer prefixes spread out requests and batch sizes reduce by 10000 tokens. SGLang:FCFS preserves low TBT as a side effect of these tiny batches, but at a steep throughput cost. SGLang:LPM and DFS-W suffer on both fronts, with TBT rising steadily due to heavier memory access and growing CPU scheduling overhead for longer prompts.

Taken together, as shared prefix lengths grow, \textsc{Feather} is the only policy that sustains both high throughput and low latency, while all baselines are forced to sacrifice one for the other.
