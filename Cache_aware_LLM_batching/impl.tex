As discussed in \S\ref{sec:motivation}, the performance of batched inference is governed not just by how many requests are executed together, but by a more subtle factor: \emph{how much prefix they share}. When requests in a batch follow a common prefix, their KV-cache accesses become highly sequential, improving both temporal and spatial locality and enabling the hardware prefetcher to better utilize memory bandwidth. In contrast, even small deviations in prefix alignment can quickly fragment these access patterns, leading to degraded throughput.

This observation suggests that \emph{the length of the shared prefix across all active requests} is a perfect metric for system performance. Longer shared prefixes directly translate into higher KV-cache reuse and more efficient memory access. However, this metric interacts in a non-trivial way with batch size: larger batches improve GPU utilization but often reduce prefix alignment. 

\subsection{Challenges and Key Ideas}
\label{sec:challenges_key_ideas}
\paragraph{Challenge 1: When to stop growing the batch?}
A natural strategy for improving throughput is to increase batch size. However, larger batches tend to include more heterogeneous requests, which reduces the shared prefix length and hurts memory locality. On the other hand, very small batches preserve strong prefix alignment but underutilize the GPU.

As described in \S\ref{sec:motivation}, moderately sized, highly homogeneous batches often outperform larger heterogeneous ones. The key question then becomes: what is the optimal batch size? More precisely, when should the scheduler stop adding requests to a batch? The answer depends on both the hardware (e.g., compute vs. memory balance) and the workload (e.g., prompt similarity), making any fixed heuristic inherently brittle.

\paragraph{Key Idea 1: Learn the stopping decision via RL}
We model batch construction as a sequential decision process and use reinforcement learning (RL) to learn when to stop. At each step, the scheduler considers adding a new request and observes (batch size, shared prefix length, prefix after addition, future-compatible requests).

There are two signals that are particularly important: (i) \textbf{Shared prefix length:} the number of tokens common across all active requests. This directly captures temporal and spatial locality. (ii) \textbf{Future compatibility:} the number of waiting requests that share the same prefix up to the new level. This indicates how many future additions can be made at \emph{zero additional locality cost}.

To build intuition, consider the following example. Suppose the current batch shares a prefix of length 10. A candidate request would reduce this to 8 (a loss of 2 tokens), which appears undesirable. However, if there are 5 additional waiting requests that also match this shorter prefix, then this one-time loss can be amortized over multiple future additions. In such cases, accepting a small immediate loss can lead to better overall throughput.

The RL policy learns to balance exactly these trade-offs, optimizing directly for decode throughput and adapting automatically to hardware and workload characteristics.

\paragraph{Challenge 2: Efficiently identifying prefix overlap.}
To make good scheduling decisions, the system must repeatedly answer: \emph{which waiting request shares the largest prefix with the current batch?} Since scheduling decisions occur frequently and the waiting queue may contain thousands of requests with long prompts, detecting prefix overlap must be extremely fast and impose minimal CPU overhead.

Modern inference systems already exploit prefix sharing for KV-cache reuse. As shown in \S\ref{sec:background}, vLLM~\cite{kwon2023efficient} uses Merkle Trees, while SGLang~\cite{zheng2024sglangefficientexecutionstructured} and BatchLLM~\cite{zheng2025batchllmoptimizinglargebatched} use radix trees to detect prefix sharing. Our scheduler, however, has a different objective: we do not need to store or manage KV-cache blocks; instead, we only need a lightweight way to estimate how much prefix overlap exists between requests so that we can select the best request to add to the batch. While a radix tree precisely captures prefix sharing, it incurs significant overhead; every insertion may trigger node splitting, and finding the best matching waiting request requires a DFS traversal that is $O(W)$ in the worst case, where $W$ is the number of waiting requests. For a scheduler making frequent decisions over thousands of long-prompt requests, that is quite expensive. Similarly, Merkle-style hash chains introduce unnecessary sequential dependencies during hash computation and expose more structure than the scheduler actually requires.

We start with a simple question: can we move away from trees? Instead of representing prefixes as paths in a tree, we divide each request into fixed-size chunks and compute prefix hashes at chunk boundaries. Each request is now represented as a sequence of hashes, and the active batch induces a \emph{working set} of hashes currently in use. This reframes the problem from tree traversal to set overlap: \emph{which request has the maximum overlap with the current working set?}

This shift eliminates structural overheads such as node splits and DFS traversal. An additional advantage of this design is that hash computation can be naturally batched and parallelized. Because chunks are processed independently, their hash contributions can be computed separately and later combined to obtain the cumulative prefix hashes. This pattern is similar in spirit to techniques such as online softmax, where partial statistics are computed over blocks and then merged to produce the final result. In contrast, Merkle-style hash chains require sequential computation because each hash depends on the previous one.

A straightforward solution is to scan all waiting requests and count how many of their hashes appear in the working set. The request with the highest overlap is selected. While correct, this approach requires $O(W \cdot C)$ work per decision (where $C$ is the number of chunks), which is too expensive for high-frequency scheduling.

\paragraph{Key Idea 2: Incremental overlap tracking via missing counts.}
To avoid repeated rescanning, we maintain for each request a \emph{missing count}: the number of its chunks not present in the working set.

Crucially, this count only changes when the working set changes (i.e., when requests are added to the batch or finished). Instead of recomputing overlap from scratch, we update these counts incrementally. This reduces the problem to finding the request with the smallest missing count.

\paragraph{Key Idea 3: Fast retrieval via lazy heap.}
To efficiently identify the best request, we maintain a min-heap over missing counts. When counts change, we push updated entries and use lazy deletion to skip stale ones.

This brings the selection cost down to $O(\log W)$ while keeping updates proportional only to affected requests.

The resulting design has two tightly coupled components: (i) A \emph{Chunked Hash representation} that transforms prefix matching into a lightweight set-overlap problem and exposes both current locality (shared prefix length) and future opportunities (compatible requests). (ii) A \emph{learning-based scheduler} that uses these signals to decide when to stop batch construction. Together, they enable the system to construct batches that are both compute-efficient and locality-aware.

\subsection{System Overview} 
\label{sec:system_overview}
Figure~\ref{fig:pipeline} illustrates the overall pipeline of our scheduling system. Our is to construct batches that simultaneously (i) keep the GPU well utilized and (ii) maximize the shared prefix length across requests, thereby improving temporal and spatial locality.

\paragraph{System model.}
We consider an inference server that continuously receives requests. Each request consists of a prompt (input tokens) followed by autoregressive decoding. Execution proceeds in iterations, where each iteration processes either prompt tokens (prefill) or generates one token per active request (decode). 
At any time, requests are partitioned into three sets:
(i) \emph{Waiting} ($W$): requests that have not yet been scheduled,
(ii) \emph{Active} ($A$): requests currently being processed on the GPU, and
(iii) \emph{Finished}: requests whose generation has completed.

The scheduler operates in repeated execution steps. In each step, it incrementally constructs a batch by selecting requests from the waiting queue and activating them. Once the batch is finalized, it is executed on the GPU for one iteration, which may correspond to either processing prompt tokens (prefill) or generating the next token for active decoding requests.

Each request is represented as a sequence of $C$ prefix hashes (chunks), derived from its token sequence of length $N$. The scheduler maintains a working set of hashes induced by the active set $A$, which defines the current shared prefix structure.

\paragraph{Unified request representation.}
All incoming requests are immediately converted into their chunked hash representation and inserted into the scheduler's data structures. Concretely, each request contributes:
(i) its hash vector,
(ii) entries in a reverse index mapping hashes to requests, and 
(iii) a missing count that tracks how much of its prefix is not yet covered by the current working set.

A global min-heap over missing counts allows the scheduler to efficiently retrieve the request with maximum overlap (i.e., minimum missing chunks) with the active batch.

\paragraph{Batch construction loop.} 
The scheduler builds batches incrementally in a loop: (i) \textbf{Select candidate.} Using the heap, the scheduler retrieves the waiting request with the highest overlap with the current working set (via \textsc{FindBest}). (ii) \textbf{Compute metrics.} For this candidate, the system computes: current shared prefix length $|P|$, the prefix length after hypothetical addition, and the number of waiting requests that would remain compatible at that level. (iii) \textbf{Decision (RL policy).} These signals are passed to the policy, which decides whether to \textsc{Add} the request or \textsc{Stop} batch construction. (iv) \textbf{Update state.} If \textsc{Add}, the request is activated, the working set is updated, and overlap statistics are incrementally maintained. Otherwise, the batch is finalized.

This loop continues until the policy decides to stop or no suitable candidates remain.

\paragraph{Execution and iteration.}
Once a batch is finalized, it is dispatched to the GPU for one execution step. After execution, the completed requests are removed from the active set, updating the working set accordingly, and the batch construction resumes by repeating the same loop. This creates a continuous scheduling cycle where batches are formed, executed, and updated in an online fashion.

\paragraph{End-to-end flow.}
Putting everything together, the system operates as follows. Incoming requests are inserted into the chunked hash structure and indexed in the heap. The scheduler repeatedly selects the best candidate based on prefix overlap, queries the policy for a decision, and either activates the request or stops batch construction. The resulting batch is executed, and the observed throughput is used to refine future decisions. This process repeats continuously as new requests arrive and existing ones complete.

The following subsections describe the prefix-overlap data structure in detail, followed by the batching policies built on top of it.

\subsection{Chunked Hash Tree}

Before diving into the operations of the Chunked Hash Tree (CHT), we must define how requests are represented and how token sequences are converted into a compact representation that captures the prefix sharing structure. As shown in Figure~\ref{fig:chunked_hash_tree_prefix_representation}, given a request with a token sequence $T = (t_1, t_2, \dots, t_N)$, we partition $T$ into non-overlapping chunks of size $K$ (e.g., $K = 50$). For each chunk boundary $\ell = 1, \dots C$ where $C = \lceil N/K \rceil$, we compute a \emph{cumulative prefix hash} at each boundary\\ $h_\ell = \mathrm{hash}(t_1, t_2, \dots, t_{\min(\ell K,\, N}), \quad \ell = 1, \dots, C$.

Because the hash is cumulative, two requests share the same $h_\ell$ if and only if their first $\ell K$ tokens are identical, which is precisely the condition under which their KV-cache prefixes can be shared. Each request $r$ is therefore represented as an ordered hash vector $H_r = (h_1^r, h_2^r, \dots, h_C^r)$. We use an incremental xxHash-64 state so that each token is processed exactly once, making the total cost $O(N)$ regardless of the number of chunked boundaries.

\subsubsection*{Inserting a request into Chunked Hash Tree}

$\textsc{Insert}$ is invoked as soon as a new request $r$ arrives at the scheduler. The goal is to register the request, compute its prefix hashes, and determine how well it aligns with the current working set.

We begin by computing the cumulative prefix-hash vector
\[
H_r = (h_1^r, \dots, h_C^r) \gets \textsc{ComputeHashes}(T, K),
\]
and storing it in \texttt{request\_hashes}, a map of request IDs to their hash vectors.

At the same time, we maintain a \emph{reverse index} \texttt{waiting}, which maps each hash $h$ to the set of \emph{waiting} requests that contain $h$. As we iterate over $H_r$, we insert $r$ into \texttt{waiting[$h$]} for every $h \in H_r$.

To evaluate how well $r$ matches the current active batch, we use the \texttt{working\_set}, which is defined as a set of tuples $(\ell, h)$ representing prefix hashes at specific levels that are currently covered by active requests. 

Using this, we compute the \emph{missing count} $m_r$, defined as the number of levels $\ell$ such that $(\ell, h_\ell^r) \notin \mathit{working\_set}$. Intuitively, $m_r$ counts how many of $r$'s prefix chunks are not already cached by the active batch. A request with $m_r = 0$ has its entire prefix covered by the current active batch and is therefore the most preferable candidate to admit next. We store this value in the \texttt{miss} map.

Finally, we insert the pair $(m_r, r)$ into \texttt{waiting\_heap}, a min-heap keyed by missing count. This allows efficient retrieval of the request that is most compatible with the current working set.

Importantly, $\textsc{Insert}$ does \emph{not} modify reference counts or the working set. These are updated only when a request transitions from waiting to active.

Figure~\ref{fig:chunked_hash_tree_insertion} shows an example of a chunked hash tree where we insert 3 requests, $R_1, R_2, R_3$. Requests $R_1, R_2$ share two levels, whereas $R_3$ just has level-1 in common with the other two. The heap has all 3 requests, each with a cost of 3.

\subsubsection*{Adding a request to the active batch}
As proposed in \S\ref{sec:challenges_key_ideas}, our key metric aims to find the number of chunks which are shared by \emph{all} requests of the active batch. In the hash tree, this corresponds to a root-anchored path that extends downward as long as every active request agrees on the hash at each level, and stops at the first level of disagreement. Since this path always starts at the root and is contiguous, it is completely determined by where it ends. We therefore maintain a single tuple $(\ell^*, h^*)$ — the \emph{shared prefix tip} — recording the depth and hash of its deepest node. An empty common prefix is denoted $\ell^* = 0$.

When request $r$ is promoted into the active batch, two things must happen: the working set must be updated to reflect $r$'s prefixes, and the shared prefix tip must be recomputed with $r$.

For the working set, any prefix hash of $r$ that is newly entering the working set (ref count zero) is inserted, and every waiting request that shares that hash gets its miss count decremented — it now has one fewer prefix chunk to warm up. Reference counts are incremented for all levels regardless.

For the shared prefix tip, the key observation is that admitting a new request can only \emph{shorten} the common prefix, never lengthen it. The new tip therefore lies at some level $\leq \min(\ell^*, |H_r|)$. To find it, we need the deepest level where $r$ agrees with the existing tip hash and that node is in the working set — this is exactly the LCA of all active request leaves in the hash trie. Searching from the bottom up finds this immediately at the first hit, allowing an early stop.

Both updates are performed in a single backward pass over $H_r$. We iterate from level $|H_r|$ down to $1$, updating the working set and miss counts at every level. Once we reach $\ell_{\mathrm{tip}} = \min(\ell^*, |H_r|)$, we additionally begin checking for LCA agreement at each level. The first level where $h_\ell^r = h^*$ and $(\ell, h_\ell^r) \in \mathit{working\_set}$ is the new tip; we record it and continue the loop — without breaking — so that all remaining levels still receive their working set updates.

Figure~\ref{fig:chunked_hash_tree_activation} shows the chunked hash tree, after we activate request $R_1$. We mark the working set nodes as green. The shared prefix tip is set to level-2 hash of $R_1$, and the newer costs of $R_2$ and $R_3$ are appended to the waiting heap.

\subsubsection*{Removing a request from the active batch}
$\textsc{Finish}$ is called when request $r$ completes. It is the symmetric counterpart of $\textsc{AddToBatch}$: where activation could only shorten the shared prefix, completion can only \emph{lengthen} it, since one fewer request needs to agree.

For the working set, we decrement the ref count of each hash in $H_r$. Any hash whose ref count drops to zero leaves the working set, and every waiting request containing that hash has its miss count incremented because that prefix chunk is no longer in the working set.

For the shared prefix tip, after removing $r$ the remaining active requests may now agree on a longer common prefix than before. Starting from $\ell^* + 1$, we walk forward level by level, checking whether all remaining active requests share the same hash at each level. The first level of disagreement — or the shortest active request — ends the extension. This forward scan is cheap in practice since the tip rarely moves more than a few levels.

Both updates are performed in a single forward pass over $H_r$ for the working set, followed by a short forward scan for the tip extension. The tip scan begins from $\ell^* + 1$ and consults the working set directly: a level $\ell$ can extend the tip only if $(\ell, h)$ is in the working set with ref count equal to $|\mathit{active}|$, meaning every remaining active request carries that hash.

\subsubsection*{Finding the Best Request}

The goal of $\textsc{FindBest}$ is to identify the waiting request that would best complement the current active batch. The key insight is that the best candidate is the waiting request whose prefix chunks are \emph{most covered} by the current active batch, i.e., the one with the smallest missing count $m_r$.

The primary selection criterion is the \emph{missing count} $m_r$: the number of prefix chunks of $r$ not yet in the working set. The waiting heap is a min-heap keyed by $m_r$, so the best candidate surfaces at the top. Since the heap uses lazy deletion, stale entries (where the recorded miss count no longer matches $\mathit{miss}[r]$) are skipped until a fresh entry is found.

Once the best candidate $r^*$ is identified, we compute three statistics to inform the caller's admission decision. The first is $\ell^*_{\mathit{before}}$, the current tip depth before admitting $r^*$. The second is $\ell^*_{\mathit{after}}$, the tip depth that would result after admitting $r^*$, found by walking backward from $\min(\ell^*, |H_{r^*}|)$ until $r^*$'s hash matches the working set — the same LCA logic as $\textsc{AddToBatch}$, but without committing the update. The third is $\mathit{peers}$: the number of other waiting requests that already share the prefix down to depth $\ell^*_{\mathit{after}}$, indicating how many future admissions would benefit at no additional tip cost.

The $\mathit{peers}$ count captures an amortization argument. If admitting $r^*$ shrinks the tip by $\Delta = \ell^*_{\mathit{before}} - \ell^*_{\mathit{after}} > 0$ levels, that is a one-time locality cost. But if $\mathit{peers} = k$ other waiting requests already share a prefix of depth $\ell^*_{\mathit{after}}$, those $k$ requests can be admitted immediately after at zero further tip cost — so the cost $\Delta$ is amortized over $k + 1$ admissions. $\textsc{FindBest}$ surfaces this trade-off for free, leaving the admission policy a single focused question: is this cost worth it right now? How different policies answer that question is the subject of \S\ref{sec:batching_rl}.

The result is cached and reused on repeated calls until the working set or waiting queue changes, avoiding redundant heap traversals.

An intuitive alternative to using the missing count is to simply select a waiting request that matches the current shared prefix tip $(\ell^*, h^*)$. The rationale is to maintain the current tip depth and prevent the shared chain from shrinking. However, this approach introduces a subtle flaw regarding future extension potential, because the tip is inherently bottlenecked by the most divergent active request. Consider a scenario where Level 0 is shared by all requests, but Level 1 splits into three distinct branches: one for $R_1$, one shared by $R_2$ and $R_3$, and a third for $R_4$. If our active batch contains $R_1$ and $R_2$, the shared prefix tip is restricted to Level 0. If we select the next request based solely on this current tip, $R_3$ and $R_4$ appear equally viable. Should the scheduler arbitrarily admit $R_4$, the tip remains at Level 0, but crucially, when $R_1$ finishes, the remaining requests ($R_2$ and $R_4$) sit on divergent branches, leaving the tip permanently stuck.

Our Chunked Hash Tree avoids this trap entirely by evaluating candidates against the complete \texttt{working\_set} using the missing count $m_r$. Rather than anchoring to a bottlenecked tip, the working set tracks every prefix chunk kept alive by any active request. In the previous example, because $R_2$ is active, its Level 1 chunk is already present in the working set. Consequently, $R_3$ requires fewer missing chunks than $R_4$, resulting in $m_{R_3} < m_{R_4}$. By selecting $R_3$, the immediate tip remains bottlenecked at Level 0, but the scheduler implicitly preserves future overlap. Once $R_1$ finishes and is removed via \textsc{Finish}, the forward scan evaluates the remaining batch $\{R_2, R_3\}$ and successfully extends the shared prefix tip to Level 1, automatically reclaiming deeper locality benefits.

Figure~\ref{fig:chunked_hash_tree_find_best_request} shows that $R_2$ was at the top of the waiting heap, and thus got selected as the best request. After adding $R_2$ to the active batch, it's nodes are appended to the working set, and the shared prefix tip is updated.

\subsubsection*{Optimizations}

\paragraph{Result caching.}
$\textsc{FindBest}()$ may be called repeatedly within a single scheduling round without any intervening state change. We cache its last result — a four-tuple \\ $(r^*,\, \ell^*_{\mathit{before}},\, \ell^*_{\mathit{after}},\, \mathit{peers})$ — and return it immediately on subsequent calls until any mutation (an activation, completion, or new insertion) invalidates the cache flag.

\paragraph{Lazy heap updates.}
When a request's missing count changes, we push a fresh $(m_r, r)$ entry onto the heap rather than updating the existing one in place. Stale entries — where the recorded $m$ differs from $\mathit{miss}[r]$ — are silently skipped during $\textsc{FindBest}$. This avoids an $O(W)$ heap search on every miss-count change, keeping $\textsc{AddToBatch}$ and $\textsc{Finish}$ at $O(C \cdot W_h \cdot \log W)$, where $W_h$ is the average number of waiting requests sharing a given hash.

\paragraph{Incremental shared prefix tip maintenance.}
Rather than recomputing the shared prefix tip from scratch after every state change — which would require scanning all active requests at $O(A \cdot C)$ cost — we exploit the asymmetry between the two events. Activation can only \emph{shorten} the tip: $\textsc{AddToBatch}$ finds the new tip via a single backward pass over $H_r$, terminating at the first working-set match. Completion can only \emph{lengthen} the tip: $\textsc{Finish}$ attempts a forward extension level by level beyond $\ell^*$, using the ref count check to test agreement across all active requests, stopping at the first disagreement. Both updates are $O(C)$ in the worst case and terminate early in practice.

\paragraph{Pre-allocation.}
All major hash tables and vectors pre-allocate capacity at construction time, eliminating rehash latency and reallocation overhead during high-throughput operation.

\subsection{Batching and Reinforcement Learning}
\label{sec:batching_rl}
\textcolor{red}{any visualizations for these RL policies needed?}

So far, the CHT provides us with an efficient way to find the best next request to add to the batch, the one that maximizes prefix reuse. But it does not tell us \emph{when to stop}. Adding more requests always increases GPU utilization, but at some point, the shared prefix starts to shrink, hurting locality. This section describes how we frame this stop/continue decision as a learning problem and present three policies of increasing complexity: a hand-crafted heuristic that encodes domain intuition, a contextual bandit that learns from experience without temporal structure, and a Q-learning agent that reasons about long-term throughput.

As highlighted in \S\ref{sec:system_overview}, the scheduler incrementally builds a decoding batch by repeatedly selecting the lowest-cost waiting request via the CHT and deciding whether to add it to the current batch or dispatch the batch as-is. This stop/continue decision is the crux of the batching problem. 

\subsubsection*{State, Actions, and Reward}
At each step of batch formation, the scheduler observes a state
\[
s = (\mathit{batch\_size},\; \mathit{chunks\_before},\; \mathit{chunks\_after},\;\mathit{requests\_waiting})
\]
and takes a binary action $a \in \{\textsc{Add}, \textsc{Stop}\}$. Here, $\mathit{batch\_size}$ denotes the number of requests that are already in the batch, which is a proxy for current GPU utilization. $\mathit{chunks\_before}$ is the shared-prefix chain length \emph{before} adding the candidate request; $\mathit{chunks\_after}$ is the chain length after hypothetically adding it (obtained from $\textsc{FindBest}$); and $\mathit{requests\_waiting}$ is the number of waiting requests that share the prefix up to level $\mathit{chunks\_after}$, indicating whether the locality cost of this addition will be compensated by future activations. Together, these four values capture both the current GPU utilization (batch size) and the cost of the proposed addition to prefix locality, summarized by the chunk loss $\Delta = \mathit{chunks\_before} - \mathit{chunks\_after}$).

Both learning policies share the same reward signal: the decode throughput of the dispatched batch,

\[
\mathcal{R} = \text{throughput}_{\mathrm{decode}}
\]

Maximizing this reward simultaneously encourages large batches (better GPU utilization) and short decode times (better prefix locality). Both policies also operate over the same discretized state space: $\mathit{batch\_size}$ and $\mathit{requests\_waiting}$ are mapped to exponential bins, while the chunk loss $\Delta$ is mapped to a coarser set of thresholds. The discretized state is a triple $(\hat{b}, \hat{\Delta}, \hat{w})$, where each hat denotes the bin index. The resulting table is small enough to store in a hash map and converges quickly, even under moderate traffic.

\subsubsection*{Heuristic Policy}
Before introducing any learning, we establish a baseline that encodes domain intuition directly as rules. The heuristic is designed around two competing goals: \emph{maximizing GPU utilization} by filling the batch as much as possible and \emph{preserving prefix locality} by avoiding candidates that cause large drops in the shared prefix chain. The heuristic always adds a candidate that does not hurt the shared chain at all—a free addition. When the batch is still very small and GPU utilization is clearly low, it tolerates a slightly larger locality cost to avoid dispatching an underutilized batch. In the general case, it accepts a candidate only if the chunk loss is within a small tolerance. Finally, when many waiting requests share the same prefix level, it allows a marginally higher locality cost since the short-term penalty is likely to be offset by the homogeneous additions that follow. If none of these conditions are met, the heuristic stops and dispatches the current batch.

This policy requires no training and converges immediately, but its thresholds are fixed and cannot adapt to shifts in workload distribution.

\subsubsection*{Contextual Bandit}
To move beyond hand-tuned thresholds, we implement a contextual bandit using Upper Confidence Bound (UCB) selection~\cite{auer2002finite}. The bandit treats each batch-construction call as an independent decision: given the discretized state $\hat{s} = (\hat{b}, \hat{\Delta}, \hat{w})$, it selects the action that maximizes
\[
  \mathrm{UCB}(\hat{s},a) = \frac{\mu(\hat{s},a)}{n(\hat{s},a)} + c\sqrt{\frac{\ln N}{n(\hat{s},a)}}
\]
where $\mu(\hat{s}, a)$ is the cumulative reward for taking action $a$ in state $\hat{s}$, $n(\hat{s}, a)$ is the number of times that pair has been selected, $N$ is the total number of steps, and $c$ is the exploration coefficient. The first term favors actions that have historically yielded high throughput; the second term ensures that under-explored actions are tried sufficiently often.

Because the bandit discards temporal structure entirely, it does not reason about how today's batching decision affects the state of the queue for the next batch, it can miss opportunities where a short-term locality sacrifice leads to a better-amortized sequence of future batches. This motivates the full reinforcement learning approach.

\subsubsection*{Q-Learning Policy}
To capture the temporal dependencies that the bandit ignores, we model batch construction as an episodic reinforcement learning problem. A new episode begins each time the scheduler starts forming a fresh batch and terminates when it issues \textsc{Stop} or the waiting queue is exhausted. The Q-table~\cite{watkins1992} stores a value $Q(s, a)$ for every (discretized state, action) pair and is updated upon each batch completion via the standard Bellman update:

\[
Q(s, a) \; \leftarrow\; Q(s, a) + \alpha\bigl[r + \gamma \max_{a'} Q(s', a') - Q(s, a)\bigr]
\]

where $r$ is the observed throughput reward, $s'$ is the state at the start of the \emph{next} batch formation, $\alpha$ is the learning rate, and $\gamma$ is the discount factor. The discount factor encodes that the agent values near-term throughput slightly more than long-term gains, which matches the real-time nature of an inference server. During training, $\varepsilon$ starts at $1.0$ (fully random) and decays linearly to $\varepsilon_{\min}$ over a configurable number of steps, after which the policy is nearly deterministic.

\subsubsection*{The \textsc{BuildBatch} Procedure}
Algorithm~\ref{alg:rl_batch} shows how all three policies fit into the same batch-construction loop. At each iteration, \textsc{FindBest} (Algorithm~\ref{alg:find_best}) is called to retrieve the lowest-cost candidate from the CHT along with its chain statistics $c_{\mathrm{before}}$, $c_{\mathrm{after}}$, and the number of waiting requests $w$ that share the same prefix level. These four values are assembled into the state $s$ and passed to whichever policy $\pi$ is active—heuristic, bandit, or Q-learning agent—which returns either \textsc{Add} or \textsc{Stop}. If \textsc{Add}, the candidate is activated and appended to the batch; if \textsc{Stop}, the loop exits and the batch is dispatched immediately. Once the batch executes, the observed decode throughput serves as the reward signal: the bandit updates its count-and-mean tables, while the Q-learning agent applies the Bellman update above. The heuristic requires no update. 

\begin{algorithm}[H]
\caption{$\textsc{BuildBatch}()$}
\label{alg:rl_batch}
\begin{algorithmic}[1]
\Require Waiting queue $Q$; policy $\pi$ (heuristic, bandit, or Q-learning); discount $\gamma$; learning rate $\alpha$
\Ensure Batch $B$ ready for one decode iteration
\State $B \gets \emptyset$
\While{$Q \neq \emptyset$}
    \State $(r^*, c_{\mathrm{before}}, c_{\mathrm{after}}, w) \gets \textsc{FindBest}()$
    \If{$r^* = \bot$} \textbf{break} \EndIf
    \State $s \gets (|B|,\; c_{\mathrm{before}},\; c_{\mathrm{after}},\; w)$
    \State $a \gets \pi(s)$ \Comment{heuristic rule / UCB look-up / $\varepsilon$-greedy Q-table}
    \If{$a = \textsc{Stop}$} \textbf{break} \EndIf
    \State $\textsc{Activate}(r^*)$;\quad $B \gets B \cup \{r^*\}$
\EndWhile
\State $\text{throughput}_{\mathrm{decode}} \gets \textsc{ExecuteBatch}(B)$
\State \textbf{Update} $\pi$ with observed reward $\text{throughput}_{\mathrm{decode}}$ \Comment{no-op for heuristic}
\State \Return $B$
\end{algorithmic}
\end{algorithm}
