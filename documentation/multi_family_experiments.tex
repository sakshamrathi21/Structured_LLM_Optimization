\chapter{Experiments - Multiple Family of Requests}
\label{ch:multi_family_experiments}
\section{Introduction}
While the previous chapter focused on workloads where all queries share a single long prefix, real-world applications often involve heterogeneous families of requests—each with its own distinct context or document. For instance, in an enterprise setting, different teams might query separate knowledge bases, or in an educational setup, multiple courses could simultaneously host LLM-based assistants trained on different lecture materials. These scenarios represent a multi-family inference workload, where each family maintains an independent prefix but shares the same model and hardware resources.

\section{How to generate such a workload?}

From the previous experiments, we already have a large system prompt of around 1500 tokens. Now, we need to perform experiments with multiple families of requests, where each family shares a large prefix in common (the system prompt).

One naive way to generate such a dataset, is to write multiple unique system prompts, each around 1500 tokens. However, for larger number of families, this becomes tedious and time-consuming.

A smart hack (Fig.~\ref{fig:family_generation}) to generate multiple families of requests, while still sharing the same system prompt, is to prepend a unique identifier (like ``AA'', ``AB'', ``AC'', etc.) to the existing system prompt. This way, each family has a unique prefix, but the majority of the content (the system prompt) remains the same across all families. Since, we do not care about the response quality in these experiments (for now), this approach is sufficient to simulate multiple families of requests with a large shared prefix.

Also, since the starting identifiers are unique for each family, the block hashes will be different, leading to separate KV Cache blocks for each family, despite most of the content being identical.

\section{Families of Requests across various models}
In our first experiment, we compare the throughput of handling multiple families of requests versus a single family with the same total number of requests. We use 10 families, each with 1000 requests, and compare it to a single family with 10000 requests. The models chosen for this experiment are Qwen 0.5B, Llama 7B and LongChat 13B. As we can see, as the model size increases, the throughput degradation when handling multiple families becomes more pronounced. This is likely due to the increased attention computation overhead from having to manage multiple KV Cache blocks for different families, which becomes more significant with larger models.


\section{Effect of Batch Decomposition on Inter-Scheduler Latency}
The observed throughput differences raise questions about why multi-family scenarios degrade performance so sharply. To better understand the internal scheduling behavior, we decompose the inference process into its constituent stages—prefix prefill, unique prefill, and decode—and examine their individual contributions to end-to-end latency.

We divide a query into 3 components - prefix prefill (prefill of the large shared prefix), prefill (of unique suffix/query) and decode (generation of tokens). We vary the batch decomposition across these 3 components and measure the time spent in each component (basically the difference of time instants between two calls to the scheduler).

As we can see from the figure, the time spent in prefix prefill is significantly higher than the other two components, which is expected since the prefix is large (around 1500 tokens). Also, the overall time spent is heavily influenced by the number of prefix prefills we have in that batch. It is more or less independent of the number of suffix prefills and decodes.

\section{Merging queries belonging to the same family into a single batch}
Through a few more trials and experiments, we found that merging queries from the same family into a single batch (basically making the batch homogeneous with respect to family IDs) leads to significant throughput improvements.

This is likely because of the fact that each family shares a large number of KV Cache blocks, so if multiple queries from the same family fit into a single batch, we will have to load a large number of KV Cache blocks from the HBM into the L2 shared cache. Since, the size of an L2 shared cache is limited, having a heterogeneous batch with queries from different families will lead to cache thrashing and evictions, leading to more HBM loads and lower throughput.


However, when we merge queries from the same family into a single batch, we reduce the number of unique KV Cache blocks needed for that batch, leading to better cache utilization and higher throughput.

Naively, we can sort the incoming queries based on their family IDs before forming batches. This way, queries from the same family are more likely to be grouped together in a batch.

\section{Varying all the parameters together}
So far, we have analyzed the influence of batch size and family composition independently. However, in practice, these factors interact—along with workload intensity—to determine overall performance. We therefore conduct a comprehensive study varying all parameters jointly to capture the combined dynamics of multi-family inference. So, we primarily have the following parameters:
\begin{itemize}
    \item Number of Families
    \item Workload - requests per second
    \item Max Batch Size
    \item The nature of the batch - whether ordered by family IDs or random permutation:
    \begin{itemize}
        \item 0: Ordered by family IDs
        \item 1: We make chunks of size 50 from the sorted list and permute each chunk randomly (allows us to have some level of prefix sharing between consecutive queries)
        \item 2: Completely random permutation
    \end{itemize}
\end{itemize}

\begin{itemize}
    \item As we can see, increasing the max batch size generally leads to higher throughput, as it allows better GPU utilization.
    \item Ordering the batches by family IDs (batch nature level 0) consistently provides the best throughput, due to improved cache locality and reduced memory bandwidth pressure.
    \item A batch nature level of 1 is roughly similar to level 2, which suggests that even a small amount of mixing in the batch (basically making the batch heterogeneous with >1 number of families) leads to significant throughput degradation.
    \item This can be justified by the fact that, all the SMs share an L2 cache of limited size, so even a small increase in the working set size (number of unique KV cache blocks needed) can lead to cache thrashing and evictions, leading to more HBM loads and lower throughput.
    \item Often a homogeneous batch of smaller size performs significantly better than a larger heterogeneous batch (for example, check batch sizes of 100 and 500 in the plots above). This essentially suggests, that if we have a heteorogeneous batch of 500, with 5 families inside it, we can possibly divide it into smaller batches of size 100, and achieve a much higher throughput.
\end{itemize}
