\section{Throughput and Latency Measurements across different techniques}
Here is the experiment setup:
\begin{itemize}
    \item Model: \texttt{TinyLlama/TinyLlama-1.1B-Chat-v1.0}
    \item System Prompt: Roughly 1500 tokens (adopted from Ostep MLFQ schedulung chapter)
    \item Queries: 100 queries, each of length 10-20 tokens
    \item Max Output Length: 80 tokens
    \item Techniques Compared: vLLM (with and without automatic prompt caching), SGLang, swiftLLM
\end{itemize}


\noindent\textbf{Algorithm: Workload Generation at Target QPS}
\begin{algorithmic}[1]
\Require LLM model \texttt{llm}, list of \texttt{prompts}, parameters \texttt{sampling\_params}, target QPS \texttt{qps}
\Ensure Latencies of requests

\State Initialize empty list \texttt{latencies}
\State $\texttt{interval} \gets 1 / \texttt{qps}$
\State $\texttt{start\_time} \gets \text{current time}$
\State $i \gets 0$
\State Initialize empty \texttt{backlog}
\State $\texttt{next\_time} \gets \text{current time}$

\While{$i < \text{length}(\texttt{prompts})$}
    \State $\texttt{now} \gets \text{current time}$
    \State $\texttt{intervals\_passed} \gets \lfloor (\texttt{now} - \texttt{next\_time}) / \texttt{interval} \rfloor + 1$
    
    \Comment{Add missed prompts to backlog if multiple intervals passed}
    \For{$k = 1$ \textbf{to} $\texttt{intervals\_passed}$}
        \If{$i < \text{length}(\texttt{prompts})$}
            \State Append $\texttt{prompts}[i]$ to \texttt{backlog}
            \State $i \gets i + 1$
        \EndIf
    \EndFor

    \If{\texttt{backlog} is not empty}
        \State $\texttt{batch\_start} \gets \text{current time}$
        \State $\texttt{llm.generate(backlog, sampling\_params)}$
        \State $\texttt{batch\_latency} \gets \text{current time} - \texttt{batch\_start}$
        \Comment{All requests in backlog share the same latency}
        \ForAll{request in \texttt{backlog}}
            \State Append $\texttt{batch\_latency}$ to \texttt{latencies}
        \EndFor
        \State Clear \texttt{backlog}
    \EndIf

    \State $\texttt{next\_time} \gets \texttt{next\_time} + \texttt{intervals\_passed} \times \texttt{interval}$
    \Comment{Sleep if ahead of schedule}
    \State $\texttt{sleep\_time} \gets \max(0,\, \texttt{next\_time} - \text{current time})$
    \State $\texttt{sleep(sleep\_time)}$
\EndWhile

\State \Return \texttt{latencies}
\end{algorithmic}

We primarily measure the following metrics:
\begin{itemize}
    \item \textbf{Throughput (QPS)}: Total number of requests / Total time taken
    \item \textbf{Average Latency (s)}: Average time taken per request, basically the time a user will have to wait
    \item \textbf{P95 Latency (s)}: 95th percentile latency across all requests, this helps us understand the tail latency, which in turn blocks the next batch of requests
\end{itemize}

\subsection{Chunked Prefill Enabled}
Once chunked prefill is enabled, the policy is changed to (\cite{vllm_chunked_prefill}):
\begin{itemize}
    \item Prioritize decode requests: It batches all pending decode requests to the batch before scheduling any prefill.
    \item When there are available token budgets (\texttt{max\_num\_batched\_tokens}), it schedules pending prefills. If the last pending prefill request cannot fit into \texttt{max\_num\_batched\_tokens}, it chunks it.
\end{itemize}

This policy has two benefits:
\begin{itemize}
    \item It improves ITL (inter token latency) and generation decode because decode requests are prioritized.
    \item It helps achieve better GPU utilization by locating compute-bound (prefill) and memory-bound (decode) requests to the same batch.
\end{itemize}


Smaller batch size achieves better ITL because there are fewer prefills interrupting decodes. Higher batch size achieves better TTFT as you can put more prefill to the batch.

\section{Maximum Throughput with vLLM}
We sent 100 requests all at once to vLLM server, and measured the number of prefills and deocodes for a single batch (batches are generated after every model run). This experiment helped us understand the scheduler algorithm of vLLM in a much better way.
 
When chunked prefill is enabled, we got a throughput of 26.04 QPS. The total time taken was 3.84s for 100 requests.

When chunked prefill is disabled, we got a throughput of 20.12 QPS. The total time taken was 4.97s for 100 requests.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.7\textwidth]{\RESULTDIR/vllm_batch_outputs.png}
    \caption{Number of batch outputs - chunked prefill disabled}
\end{figure}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.7\textwidth]{\RESULTDIR/vllm_batch_outputs_chunked_prefill.png}
    \caption{Number of batch outputs - chunked prefill enabled}
\end{figure}

As we can see from the above plots, when chunked prefill is disabled, we perform all the prefill operations in the start itself (because of large token sizes, and small number of max batched tokens, we can't afford more than one prefill in a single batch). After all the prefills are performed, we move to the decoding stage, where each new request just takes a size of one token, leading to a lot of decode operations in a single batch.

When chunked prefill is enabled, we are able to interleave prefill and decode operations better, leading to improved GPU utilization and throughput.



\section{Throughput vs Load Comparison For vLLM}

From now on, we enable automatic prefix caching in vLLM for better performance (switched from vLLM v0 to vLLM v1 engine).


In the following experiment, we compare the throughput in three cases: 
\begin{itemize}
    \item vLLM with prefix caching and chunked prefill enabled
    \item vLLM with just chunked prefill enabled
    \item vLLM with no optimizations
\end{itemize}

We vary the load (QPS) from 5 to 500, and measure the achieved throughput.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.7\textwidth]{\RESULTDIR/throughput_comparison_vllm.png}
    \caption{Throughput vs Load}
\end{figure}

As we can see from the plot above, with prefix caching enabled, we are able to achieve much higher throughput at higher loads, for example the max we reached was around 235 QPS, whereas without prefix caching, the max we reached was just around 30 QPS.

This is because, our workload has a large common prefix, which no longer needs to be recomputed for every request, leading to significant speedups.

The improvement of chunked prefill for larger loads is negligible.


Next, we compared different models (TinyLlama-1.1B, Llama-2-7B) for varying workloads (again with prefix caching and chunked prefill enabled). As we can see, larger models have lower throughput due to higher compute requirements. They have larger number of attention heads and layers, leading to more compute intensive operations.

\section{Compute Utilization across various max batch sizes}
To get a better idea of how well vLLM utilizes the GPU across differe max batch sizes (number of requests we can fit into a single scheduler batch), we measured two metrics - SM Activity and SM Occupancy through NVIDIA DCGM (\cite{nvidiadcgmi}). As we can see, for smaller models (such as Qwen 0.5B used in this case), the compute utilization stops increasing drastically after a batch size of 1000 requests. Increasing the batch size further doesn't help much, as the model is already able to saturate the GPU compute. However, for larger models, this threshold will be much lower (for example around 100 requests for Llama-2-7B).
